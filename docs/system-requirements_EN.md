# System Requirements

Use this page before installing VictoriaMetrics, Grafana, or the EVCC dashboards. The commands remain in the dedicated install and migration guides; this page only collects the prerequisites in one place.

## Supported Setup

Recommended production shape:

- one VictoriaMetrics instance per EVCC instance
- one Grafana instance with the VictoriaMetrics datasource plugin
- EVCC raw metrics written to VictoriaMetrics in Influx line protocol
- daily `evcc_*` rollups generated by `evcc-vm-rollup.py`

Do not multiplex multiple EVCC systems into one VictoriaMetrics instance with a synthetic `db` label. The dashboards and rollup tools assume one dedicated VictoriaMetrics namespace per EVCC system.

## Minimum Runtime Versions

| Component | Requirement | Notes |
| --- | --- | --- |
| VictoriaMetrics | current single-node release used by the install guide | Debian guide currently validates `v1.139.0`; Docker guide may pin its own tested image tag. |
| `vmctl` | same VictoriaMetrics release family as the target VictoriaMetrics version | Needed for InfluxDB history migration. |
| Grafana | 13.0.1 or newer | Required. The deployable dashboards use Grafana 13 tab navigation; dashboard set selection is no longer supported. |
| Grafana plugin | `victoriametrics-metrics-datasource` | Required for the `vm-evcc` datasource. |
| Python | 3.11 or newer | Needed for migration checks, label cleanup, and rollups. |
| Docker | current Docker Engine or Docker Desktop | Only needed for the Docker install path or disposable validation containers. |
| Debian | Debian 13 for the Debian install guides | Debian 13 is the validated Linux baseline for the current release preparation. |

## Hardware Sizing

Small EVCC setups are not CPU-heavy, but the historical rollup job can be memory-heavy.

Recommended minimum for a normal production host:

- 2 CPU cores
- 4 GB RAM
- persistent SSD or reliable flash storage
- enough disk space for the imported InfluxDB history plus VictoriaMetrics retention

For Raspberry Pi-class systems:

- Raspberry Pi 4 with 4 GB RAM or comparable hardware is the practical minimum
- Raspberry Pi 3 and 1-2 GB systems are not recommended for the monthly `--replace-range` rollup path

Observed reference from the real migration validation:

- raw import: about 5.3 GB transferred from InfluxDB into VictoriaMetrics
- rollup backfill: about 1.25 GB peak Python process RAM on a real multi-year EVCC history

Plan additional memory for the operating system, VictoriaMetrics, Grafana, Telegraf, and other services running on the same host.

## Network And Ports

| Service | Default port | Purpose |
| --- | --- | --- |
| VictoriaMetrics | `8428` | API, ingest, VMUI, Grafana datasource target |
| Grafana | `3000` | Dashboard UI and API |
| InfluxDB v1 source | `8086` | Read-only source during history migration |
| Telegraf listener | usually `8086` | Optional live fan-out endpoint for EVCC writes |
| EVCC UI/API | usually `7070` | Optional dashboard link and manual topology checks |

Grafana must be able to reach VictoriaMetrics. In Docker Desktop, `localhost` inside the Grafana container points to Grafana itself. Use `host.docker.internal` or a shared Docker network name for the VictoriaMetrics datasource URL.

If EVCC or Telegraf writes from another host, use the VictoriaMetrics host IP or DNS name, not `localhost`.

## Data Path Requirements

VictoriaMetrics needs persistent storage:

- Debian guide: `/var/lib/victoria-metrics`
- Docker guide: a host-mounted volume such as `/opt/victoriametrics/data` or `C:\evcc\victoriametrics\data`

Grafana also needs persistent storage for users, datasources, folders, and dashboards:

- Debian package: managed by the Grafana package paths
- Docker guide: a host-mounted volume such as `/opt/grafana/data` or `C:\evcc\grafana\data`

Do not run production data on disposable container storage unless the data can be recreated deliberately.

## Label Hygiene Requirements

The live and migrated VictoriaMetrics data must not contain infrastructure-only labels that change dashboard grouping.

Required:

- keep EVCC business labels such as `loadpoint`, `vehicle`, `id`, and `title`
- avoid synthetic `db` labels in VictoriaMetrics
- avoid Telegraf-added `host` labels by setting `omit_hostname = true` in the Telegraf `[agent]` section
- use `[[outputs.http]]` with `data_format = "influx"` for Telegraf-to-VictoriaMetrics writes

Do not use `[[outputs.influxdb]]` for VictoriaMetrics in this dashboard stack. It can create a `db` label and break the expected one-EVCC-instance-per-VM model.

## Migration Requirements

For an InfluxDB-to-VictoriaMetrics migration you need:

- read access to the existing InfluxDB v1 query API
- write access to the new VictoriaMetrics instance
- `vmctl`
- Python 3.11 or newer
- enough time and disk space for the full selected history range

Use a closed import and comparison window. If EVCC still writes to InfluxDB while the import runs, compare against a finished timestamp, not the moving current hour.

## Grafana Requirements

Grafana should have:

- VictoriaMetrics datasource UID `vm-evcc`, or the deployer must be configured with the actual UID
- datasource URL pointing to VictoriaMetrics from Grafana's point of view
- service-account token or local admin credentials for dashboard deployment
- folder `EVCC` for the deployed dashboards

The deployers always install the Grafana 13 tab-navigation dashboards from the fixed manifest file list. Dashboard set selection is no longer supported.

Grafana versions older than 13.0.1 are no longer supported by the deploy manifest.

## Post-Install Validation

At minimum, validate:

- VictoriaMetrics `/health` returns `OK`
- Grafana `/api/health` returns `database: ok`
- Grafana datasource health check returns `Data source is working`
- `check_data.py` reports required raw metrics and no `host` or `db` label issues
- `compare_import_coverage.py` reports no repo-relevant import problems
- rollup backfill dry-run returns `GO` before running `--write`
- dashboards are visible in the `EVCC` folder
